# Literature-first planning and frozen test sets

The research workflow uses three bounded GPT-4.1 mini requests: literature search, a tool proposal after test-set construction, and interpretation after the measured pilot. The worker owns approvals, execution, project-wide request limits, and deterministic pilot gates. The planner has no shell, scientific execution, or mutation tools. Development tests use fake Responses clients; they do not spend API credits.

Future public `reason` and `summary` responses are prompted as 1–2 short sentences: connect the protein evidence and actual test-set scope to the proposed method or measured pilot outcome, then give the key caveat. For example, when supported: “The ABL literature and our reference-pose control support proposing Vina for local pose recovery. Affinity accuracy remains unvalidated.” Details remain in candidates, citations, source excerpts, test-set fit, uncertainties, and questions. The prompt receives explicit measured-record, reference-control and held-out counts plus the available docking engines. It must not describe missing assay data as a constructed affinity benchmark or one available engine as a comparative winner. These are prompt/schema-description changes, not new output fields or length validation; existing stored responses remain compatible and are not rewritten.

`research_literature(spec, tool_catalog, emit, *, cancelled, client, source_client)` requires hosted Responses search with `tool_choice="required"`, at most four hosted calls, and `include=["web_search_call.action.sources"]`. It requires an actual completed search and allowed citation annotations. Failure or unsupported search blocks selection; there is no silent fallback to model memory. [Official OpenAI documentation](https://developers.openai.com/api/docs/guides/tools-web-search) lists GPT-4.1 mini support and describes its non-reasoning search path. This is a bounded literature review, not an exhaustive autonomous deep-research service.

The local live compatibility check rejected the newer `web_search` definition for the configured GPT-4.1 deployment. Models whose names begin with `gpt-4.1` therefore use the documented legacy `web_search_preview` tool; other configured models use `web_search` with an explicit hosted domain filter. **The preview route has no server-side domain filter.** Both routes independently allowlist returned source/citation URLs and every later HTTP source fetch; this restricts accepted evidence but does not restrict every page the hosted preview tool may consult. The model identity is preserved, and the app does not silently switch models or automatically retry paid requests. Request traces record the actual tool definition. Compatibility errors retain safe parameter/code fields and a bounded, credential-redacted diagnostic only for HTTP 400 errors involving `tools`.

The UI receives actual `model_call`, `tool_call`, `model_delta`, `research_sources`, and `decision_summary` events. Deltas contain public answer text. Private reasoning events are ignored. Search source records retain URLs, stable evidence IDs, citation positions, retrieval time, and the actual tool actions. Up to four cited primary pages are then fetched with 500 KB response and 6,000-character excerpt limits, bounded request time, and every redirect checked against the same allowlist. Only HTML/plain text is accepted; executable and navigation markup is discarded. The source reader does not receive API credentials. Successful reads are labeled `page_text_excerpt` or `abstract_page_excerpt`; blocked pages retain `search_excerpt` with a visible failure reason. All remain `full_text_retrieved=false`, because a bounded excerpt is not verified complete-article access. Tool selection receives these actual excerpts. Search summaries and every supplied document are untrusted data. Citation linkage validates that sources were returned, not that every scientific claim is entailed.

`build_testset(snapshot, *, seed=42, max_compounds=24, organism=None)` uses real `data.measurements` and `data.assays`, with compound structures from the measurement or matching `data.compounds`. It selects one cohort with identical target, assay, species, endpoint, construct, format and conditions. Missing species/structure/provenance and unsupported measurements remain visible exclusions. Exact measurements may enter a quantitative partition; censored relations remain in the manifest without fabricated exact values. Conflicting same-structure replicates are excluded rather than averaged. Repeated equivalent records are deduplicated with their source IDs retained.

Generic Murcko scaffold groups are separated between tuning and evaluation using the recorded seed. All acyclic compounds share one conservative group. This limits scaffold leakage but does not certify the absence of all analog leakage. Untested compounds never receive inactive labels; only explicit provider `tested_active` and `tested_inactive` annotations are retained. No activity thresholds are inferred. IC50 and EC50 remain assay-response endpoints and cannot establish Kd/Ki affinity accuracy.

The manifest contains actual records, exclusions, cohort alternatives, registered input-file hashes, reference-pose controls, partitions and frozen criteria. `dataset_sha256`, `criteria_sha256`, and `manifest_sha256` are checked by `validate_testset` before model selection or pilot interpretation. The small quantitative set is a preview, not a completed benchmark. Criteria are explicit PoC defaults for scientist review; the selected model cannot rewrite them.

The bundled 1IEP example can support a reference-pose pilot: top-ranked symmetry-aware RMSD at most 2 Å, physical validity, and a score for every reference. It does not supply an independent labeled affinity or screening benchmark. Its status remains `software_only`, and proceeding requires explicit exploratory scope. Predictive affinity and screening criteria are deliberately unset (`requires_separate_scientist_approved_protocol`), because suitable sample sizes and performance cutoffs depend on the research question. They need a separately frozen protocol before any held-out predictions are examined. Passing pose recovery cannot promote the run to validated screening or affinity prediction.

`recommend_tools(spec, literature, testset, capabilities, emit, *, cancelled, client)` takes the frozen manifest and measured capabilities. It returns candidates, selected docking/affinity IDs, public reasons, source IDs, uncertainties and focused questions. Unknown sources or engines and unavailable selections are rejected. An unavailable engine is never silently substituted. `review_pilot(spec, literature, testset, plan, pilot, emit, *, cancelled, client)` returns a public interpretation and `proceed_exploratory`, `revise`, or `need_data`. Its strict response schema has no computed-metric fields and no predictive-validation success status. The worker's measured gates remain authoritative.

Model-generated questions use explicit application controls: continue with the frozen inputs, or pause to revise them. The original question and suggested options remain visible as context; free-form replies cannot silently alter parameters or approve execution. Before a pilot has completed, a revision keeps the same job pending while replacement scientific files or measured-assay CSV are uploaded. A separate rebuild control shows its one-request model cost and the remaining project budget. Only that action invalidates the unexecuted test-set/proposal stages and resumes the same job. Previous immutable artifacts and stage outputs are retained in revision history. Questions about the revised proposal bind the new test-set hash and revision number, so old answers cannot approve changed inputs. Completed pilot inputs remain immutable and require a new research conversation for revision.

## Scientific distinctions carried into the prompt

- Vina and AutoDock4 have different search/scoring implementations. Vina's AD4 scoring option is not the AutoDock4 executable. See the [Vina method paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC10683950/) and [AutoDock4 method paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC2760638/).
- GNINA provides CNN pose scoring and affinity outputs with distinct meanings. Neither is a measured binding constant. Exact version, models and preprocessing matter. See the [author-maintained GNINA repository](https://github.com/gnina/gnina) and [GNINA method paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC8191141/).
- Uni-Dock is designed for GPU-accelerated docking; eligibility depends on this host's detected runtime and reviewed native inputs. See the [Uni-Dock repository](https://github.com/dptech-corp/Uni-Dock).
- PLANET means Protein-Ligand Affinity prediction NETwork. Its published implementation combines a 3D protein-pocket graph with a ligand's 2D graph, so it should not automatically be described as a docked-pose rescoring method. Inputs, weights and training overlap need review. See the [PLANET repository](https://github.com/ComputArtCMCG/PLANET).
- MM/PBSA and MM/GBSA require parameterized systems and sampling, with protocol-dependent uncertainty. A docking SDF is insufficient. See the [primary comparative benchmark](https://pmc.ncbi.nlm.nih.gov/articles/PMC3029230/) and [Amber documentation](https://ambermd.org/tutorials/advanced/tutorial3/).

The prompt is versioned in `biocentric/prompts/research-v2.md`. The exact prompt hash is recorded with each request. Model budgets count attempts before sending, so failed and cancelled requests cannot disappear from the project budget.
